## Phase Details

### Phase 13: argument-value-matching
**Goal**: Users can detect insecure API usage via argument values — TLS/crypto misuse and permissive file permissions fire as CWE findings without requiring cppcheck
**Depends on**: Phase 12 (lexical scanner and SastFinding pipeline)
**Requirements**: ARGVAL-01, ARGVAL-02, ARGVAL-03, ARGVAL-04, ARGVAL-05
**Success Criteria** (what must be TRUE):
  1. Running the scanner on C/C++ source containing `SSL_CTX_set_verify(..., SSL_VERIFY_NONE, ...)` produces a CWE-295 finding in the CycloneDX output and static analysis report
  2. Running the scanner on source calling `curl_easy_setopt` with `CURLOPT_SSL_VERIFYPEER` and value `0` produces a CWE-319 finding
  3. Running the scanner on source containing `umask(0)` or a permissive `SetSecurityDescriptorDacl` call produces a CWE-732 finding
  4. A division expression with a literal `/0` or `%0` constant produces a CWE-369 finding
  5. A `CweRule` entry with no `arg_value_contains` field continues to fire on name match alone (existing lexical rules are unaffected)
**Plans:** 1/1 plans complete
- [x] 13-01-PLAN.md — Extend cwe_scanner with arg_value_contains, add CWE-295/319/732/369 detection (ARGVAL-01..05)

### Phase 14: cppcheck-integration
**Goal**: Users with cppcheck installed get dataflow-backed findings merged into the same output pipeline; users without cppcheck see a warning and still get lexical results
**Depends on**: Phase 13 (argument-value matching; complete SastFinding pipeline)
**Requirements**: CPPCHECK-01, CPPCHECK-02, CPPCHECK-03, CPPCHECK-04, CPPCHECK-05
**Success Criteria** (what must be TRUE):
  1. When cppcheck is on PATH, the scanner invokes it on component-mapped C/C++ directories and cppcheck findings appear as SastFinding entries in the CycloneDX output and static analysis report
  2. When cppcheck is not on PATH (or not at the `--cppcheck-path` location), the scanner prints a warning to stderr and completes with lexical-only results — no abort, exit code 0
  3. Specifying `--cppcheck-path /custom/cppcheck` causes that binary to be invoked instead of PATH lookup
  4. A file:line:CWE tuple that appears in both lexical and cppcheck results appears exactly once in all outputs (no duplicate finding entries)
**Plans:** 5/5 plans complete
- [x] 14-01-PLAN.md — Wave 0: SastSource enum + source field on SastFinding; update all literal construction sites (CPPCHECK-02 prerequisite)
- [x] 14-02-PLAN.md — Wave 1: parse_cppcheck_xml + CPPCHECK_CWE_OVERRIDES table + parser unit tests (CPPCHECK-02)
- [x] 14-03-PLAN.md — Wave 1: --cppcheck-path CLI flag in cli.rs (CPPCHECK-04)
- [x] 14-04-PLAN.md — Wave 2: run_cppcheck_scanner subprocess runner + graceful-degradation tests (CPPCHECK-01, CPPCHECK-03)
- [x] 14-05-PLAN.md — Wave 3: deduplicate_sast_findings helper + main.rs wiring (CPPCHECK-01, CPPCHECK-05)

### Phase 15: sarif-output
**Goal**: SAST findings are written to a SARIF 2.1 file that IDEs and CI tools can consume directly alongside the existing markdown report
**Depends on**: Phase 14 (unified SastFinding stream from lexical + cppcheck)
**Requirements**: SARIF-01, SARIF-02, SARIF-03
**Success Criteria** (what must be TRUE):
  1. After a scan completes, a `_static_analysis.sarif` file exists alongside `_static_analysis.md` and contains all SastFindings in SARIF 2.1 schema
  2. Specifying `--sarif-output /path/to/output.sarif` writes the SARIF file to that path instead of the default
  3. The SARIF `runs[0].tool.driver.rules[]` array contains one entry per detected CWE with `id`, `name`, and `helpUri` pointing to `https://cwe.mitre.org/data/definitions/<N>.html`
**Plans:** 2/2 plans complete
- [x] 15-01-PLAN.md — Create SARIF writer module + unit tests (SARIF-01, SARIF-03)
- [x] 15-02-PLAN.md — Add --sarif-output CLI flag + wire main.rs call sites (SARIF-02)

### Phase 17: v1.0.17 Bug Fixes

**Goal:** Address bugs discovered during v1.0.17 verification. Ships as a patch within the v1.0.17 milestone before merge to master.
**Requirements:** AUTOSAR arxml parsing, version extraction, dedup
**Depends on:** Phases 13–16 (complete)
**Plans:** 1 (complete)

**Bugs fixed (2026-05-11):**
- **BUG-01:** `.arxml` files detected for project identification but never parsed for dependencies. Fixed: new `src/parsers/c/arxml.rs` extracts `SHORT-NAME` from `SW-COMPONENT-PROTOTYPE` and `BSW-MODULE-DESCRIPTION`. *(fixed 2026-05-11, commit 8d3f961)*
- **BUG-02:** arxml parser only handled `SW-COMPONENT-PROTOTYPE` and `BSW-MODULE-DESCRIPTION` elements. SWC type definition elements (`APPLICATION-SW-COMPONENT-TYPE`, `ECU-ABSTRACTION-SW-COMPONENT-TYPE`, etc.) in per-component arxml files were not extracted. *(fixed 2026-05-11, commit 4022e3b)*
- **BUG-03:** AUTOSAR dependencies always showed `@ unspecified`. Fixed: `.epd` `REVISION-LABEL` and Doxygen `SW Version` headers now populate real versions. AUTOSAR_SampleProject_S32K144 shows 17/18 components with real versions. *(fixed 2026-05-11, commit 14e60a5)*
- **BUG-04:** System linker deps (-lAdc, -lGpt, SWC dirs) duplicated autosar-ecosystem entries. Fixed: post-walk pass upgrades system deps to autosar ecosystem using epd/doxygen versions; shadowed system entries dropped. *(fixed 2026-05-11, commits b15067b, 9ba0c2b, d8ca713)*
