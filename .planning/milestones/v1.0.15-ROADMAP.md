## Phase Details

### Phase 6: AUTOSAR Detection
**Goal**: The scanner can reliably determine that a scanned source tree is an AUTOSAR project before any classification or output work begins
**Depends on**: Nothing (first phase of v1.0.15)
**Requirements**: DET-01, DET-02, DET-03
**Success Criteria** (what must be TRUE):
  1. Scanning a tree containing .arxml files causes the tool to flag the project as AUTOSAR
  2. Scanning a tree with directories named BSW/, MCAL/, RTE/, AUTOSAR/, or SWC/ causes the AUTOSAR flag to be set
  3. Scanning a CMakeLists.txt or Makefile that references AUTOSAR_VERSION or AR_VERSION causes the AUTOSAR flag to be set
  4. Scanning a plain C project with none of the above signals does not spuriously set the AUTOSAR flag
**Plans**: 1 plan
- [x] 06-01-PLAN.md — Add ScanContext.is_autosar field, implement detect_autosar pre-pass in scanner/mod.rs, wire from main.rs, and add 6 unit tests covering DET-01/02/03 + negative + substring + vendor-exclusion cases

### Phase 7: AUTOSAR Classification & Output
**Goal**: Every detected AUTOSAR component is classified by BSW module name, layer, and platform, and those attributes appear in the SBOM and report
**Depends on**: Phase 6
**Requirements**: CLS-01, CLS-02, CLS-03, OUT-01, OUT-02
**Success Criteria** (what must be TRUE):
  1. A component whose name matches a curated BSW module (e.g. NvM, Com, PduR) is identified as an AUTOSAR BSW component in output
  2. Each matched AUTOSAR component carries an autosar:layer property (e.g. BSW-Memory, BSW-Communication, MCAL, RTE, OS)
  3. Each matched AUTOSAR component carries an autosar:platform property (Classic or Adaptive)
  4. The scan report includes an AUTOSAR ecosystem bucket alongside existing buckets (SYSTEM, VENDORED, etc.)
  5. SPDX 2.3 and CycloneDX 1.5 output each include autosar:layer and autosar:platform properties per AUTOSAR component
**Plans**: 4 plans
- [x] 07-01-PLAN.md — Add AutosarMetadata struct + Option<AutosarMetadata> field on Dependency; propagate autosar_metadata: None to every Dependency struct literal in src/ and tests/
- [x] 07-02-PLAN.md — Bundled bsw_modules.yaml + classifier::autosar module (BswConfig, classify_autosar_components) + --bsw-config CLI flag + 8 unit tests for CLS-01/02/03
- [x] 07-03-PLAN.md — CycloneDX add_autosar_properties + SPDX OTHER ExternalRef entries (autosar:layer, autosar:platform) + format tests for OUT-02
- [x] 07-04-PLAN.md — Wire classify_autosar_components into main.rs gated on is_autosar + 2 end-to-end integration tests for OUT-01 (positive + negative gating)
**UI hint**: yes

### Phase 8: Supplier Config
**Goal**: Users can map component names to supplier strings via a YAML config file; components without a mapping emit NOASSERTION for autosar:supplier
**Depends on**: Phase 7
**Requirements**: OUT-03
**Success Criteria** (what must be TRUE):
  1. User can pass a --supplier-config flag pointing to a YAML file of component-name → supplier-name pairs
  2. An AUTOSAR component whose name appears in the config file carries the mapped supplier string as autosar:supplier in SBOM output
  3. An AUTOSAR component with no entry in the config (or when no config file is provided) emits NOASSERTION for autosar:supplier
**Plans**: 3 plans
- [x] 08-01-PLAN.md — Add SupplierResolver module, --supplier-config CLI flag, lib/main module registration, and Option<SupplierResolver> construction in main.rs (with 6 unit tests + 4 CLI integration tests)
- [x] 08-02a-PLAN.md — Verify Phase 7 contract; refactor formatter signatures to accept Option<&SupplierResolver>; thread supplier_resolver.as_ref() through all 5 main.rs formatter call sites
- [x] 08-02b-PLAN.md — Emit autosar:supplier as CycloneDXProperty and SPDX ExternalRef (OTHER) with NOASSERTION fallback; 8 formatter unit tests + 1 cyclonedx-json e2e test

### Phase 9: CVE→CWE Enrichment
**Goal**: Every CVE discovered during scanning is enriched with CWE IDs from NVD, and those IDs are visible in all three output formats
**Depends on**: Nothing (independent of Phases 6–8; can run in parallel, but sequenced here for release coherence)
**Requirements**: CWE-01, CWE-02, CWE-03, CWE-04
**Success Criteria** (what must be TRUE):
  1. For a CVE with a known CWE in NVD (e.g. CVE-2021-44228 → CWE-917), the tool retrieves and attaches the CWE ID
  2. SPDX 2.3 vulnerability output includes an ExternalRef entry of type CWE for each enriched CWE ID
  3. CycloneDX 1.5 vulnerability output populates the cwes field for each vulnerability with CWE IDs
  4. The markdown/console report shows each CWE ID alongside its parent CVE entry
  5. A CVE with no CWE in NVD produces no error; CWE fields are simply omitted for that entry
**Plans**: 2 plans
- [x] 09-01-PLAN.md — Implement src/vulnerability/nvd.rs with enrich_cwe_ids + 6 unit tests covering CWE-01 (CVE extraction, NVD-CWE placeholder filtering, set-union dedup merge, empty-weaknesses no-error, no-CVE skip)
- [ ] 09-02-PLAN.md — Re-export enrich_cwe_ids from vulnerability/mod.rs, wire call site into main.rs after OSV pass, human-verify CWE-917 appears in SPDX ExternalRef + CycloneDX cwes + markdown report against log4j fixture

### Phase 10: Internal Feature Gate
**Goal**: CVE scanning and CWE enrichment are gated behind a `cargo feature = "internal"` flag; the public binary compiles without any vulnerability code; the public-release workflow is simplified to rely on the compiler rather than a strip script
**Depends on**: Phase 9
**Requirements**: GATE-01, GATE-02, GATE-03, GATE-04
**Success Criteria** (what must be TRUE):
  1. `cargo build --release` (no feature flags) produces a binary with zero vulnerability scanning code paths
  2. `cargo build --release --features internal` produces a binary with full CVE + CWE functionality
  3. `build-release.yml` passes `--features internal` for the internal binary build
  4. `public-release.yml` strip script is simplified — it verifies `internal` is not in Cargo.toml default features instead of deleting source files
  5. The existing audit step in `public-release.yml` passes cleanly against the feature-gated source

### Phase 11: Lexical Scanner
**Goal**: Users can run the tool against a C/C++ project and receive CWE findings for 11 dangerous-function categories, scoped to component-mapped directories, with the scanner absent from the public binary
**Depends on**: Phase 10
**Requirements**: SCAN-01, SCAN-02, SCAN-03, SCAN-04, SCAN-05, SCAN-06, SCAN-07, SCAN-08, SCAN-09, SCAN-10, SCAN-11, SCAN-12, SCAN-13, SCAN-14, SCAN-15, QA-01
**Success Criteria** (what must be TRUE):
  1. Running the tool with `--features internal` against a C/C++ source tree produces CWE findings for each triggered rule (CWE-120/242, CWE-134, CWE-78, CWE-327, CWE-377, CWE-190, CWE-22, CWE-676, CWE-362/367, CWE-20, CWE-126, CWE-807)
  2. Findings reference only files within the component-mapped C/C++ directories; files outside those directories are not scanned
  3. Running `cargo build --release` (no feature flags) produces a binary with no scanner code paths compiled in
  4. False positive rate on the xcar-linux corpus is reviewed and the rule set is adjusted before output wiring begins (QA-01 gate)
**Plans**: TBD

### Phase 12: Output & Report
**Goal**: Scanner findings are surfaced in CycloneDX 1.5 vulnerabilities[], a dedicated `_static_analysis.md` report, and a CLI disclaimer; SPDX output and `_report.md` are confirmed unchanged; xZETA ingestion behavior is validated
**Depends on**: Phase 11
**Requirements**: OUT-01, OUT-02, OUT-03, OUT-04, OUT-05, OUT-06, QA-02
**Success Criteria** (what must be TRUE):
  1. CycloneDX output includes a `vulnerabilities[]` entry per finding with `cwes[]`, `affects[].ref` to the component bom-ref, `source.name = "radeis_sc2sbom static analysis"`, and `analysis.state: "in_triage"`
  2. Each CycloneDX finding entry carries `properties` entries for `sc2sbom:finding:file`, `sc2sbom:finding:line`, and `sc2sbom:finding:function`
  3. Running with `--all` format flag produces a `_static_analysis.md` file containing a per-component CWE summary table and a file:line findings list
  4. CLI stdout includes the disclaimer "Pattern-based — complex data-flow vulnerabilities not covered" when static analysis runs
  5. SPDX 2.3 output and `_report.md` are byte-for-byte equivalent to their pre-v1.0.16 output on a project with no C/C++ findings (OUT-05, OUT-06 confirmed); xZETA ingests non-CVE vulnerabilities[] entries without error (QA-02 gate)
