<objective>
Extend `ScanContext` with the `component_dirs` mapping that downstream lexical scanning depends on, and populate it at every C/C++ parser call site inside `scan_directory`. This is the foundation for SCAN-05 (scope restriction): the lexical scanner consumes this map; without it the scanner has no input.

Per D-01, D-02, D-03, the field is `HashMap<(String, String), PathBuf>` keyed by `(dep.name, dep.ecosystem)` — exactly mirroring the `dep_to_bom_ref` key pattern in `cyclonedx.rs` so the formatter can resolve `affects[].ref` later in Plan 03.

Per Pitfall 5 in 11-RESEARCH.md, the field is **unconditional** on `ScanContext` (it uses only stdlib types and is zero-cost when empty). Only the consumer (lexical scanner) and its main.rs invocation are gated behind `#[cfg(feature = "internal")]`.

Purpose: Provide the scope source for the lexical scanner so SCAN-05 (component-mapped dirs only) is enforceable.
Output: `ScanContext.component_dirs` is populated for every C/C++ dep produced by the six C/C++ parsers; tests on both feature variants pass.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Filesystem -> scanner | User-supplied scan path may contain symlinks, deeply nested dirs, or unusual filenames. The existing `should_process_entry` and `warn_on_walkdir_err` patterns already harden this boundary; this plan does not change that. |
| Parser output -> ScanContext | Untrusted dep names/ecosystems come from manifest content. `(String, String)` keys are inert; no shell, SQL, or path interpolation occurs at this layer. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-11-01-01 | Tampering | component_dirs key collision via two manifests using the same (name, ecosystem) | accept | `entry().or_insert_with(...)` keeps the first parent; deterministic and matches D-03 first-discovery semantics. No security impact. |
| T-11-01-02 | Information Disclosure | A malicious symlinked manifest could record a parent directory outside the scan root | mitigate | Walker is initiated from `path` (the user-supplied scan root) under existing `should_process_entry` filtering; `parent()` is always a descendant of that root. No new traversal added. |
| T-11-01-03 | DoS | Pathological repository with millions of C/C++ manifests inflates HashMap | accept | HashMap entries are small ((String, String) -> PathBuf); RAM cost grows linearly with manifest count, dominated by existing `all_dependencies` accumulator. No new amplification factor. |
</threat_model>
