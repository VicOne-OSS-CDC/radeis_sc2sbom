# Requirements: radeis_sc2sbom

**Defined:** 2026-05-08
**Milestone:** v1.0.15 — AUTOSAR Support & CVE Enrichment
**Core Value:** Accurate, spec-compliant SBOM output that downstream consumers (xZETA, compliance tools) can ingest without errors.

## v1.0.15 Requirements

### AUTOSAR Detection

- [ ] **DET-01**: Tool detects AUTOSAR project via presence of .arxml files anywhere in the scanned tree
- [ ] **DET-02**: Tool detects AUTOSAR project via directory names matching BSW/, MCAL/, RTE/, AUTOSAR/, SWC/
- [ ] **DET-03**: Tool detects AUTOSAR project via AUTOSAR_VERSION or AR_VERSION variables in CMake/Makefile build files

### AUTOSAR Classification

- [ ] **CLS-01**: Tool matches discovered component names against a curated BSW module list (NvM, MemIf, Com, PduR, CanIf, Os, Rte, EcuM, Det, etc.)
- [ ] **CLS-02**: Tool classifies each matched AUTOSAR component into a BSW layer (MCAL, BSW-Services, BSW-Communication, BSW-Memory, RTE, OS, Complex Drivers)
- [ ] **CLS-03**: Tool tags each AUTOSAR component as Classic AUTOSAR or Adaptive AUTOSAR platform

### AUTOSAR Output

- [ ] **OUT-01**: Report surfaces a distinct AUTOSAR ecosystem bucket alongside existing buckets (SYSTEM, VENDORED, etc.)
- [ ] **OUT-02**: SPDX 2.3 and CycloneDX 1.5 output includes autosar:layer, autosar:platform, and autosar:supplier properties per AUTOSAR component
- [x] **OUT-03**: User can provide a YAML supplier-mapping config file (component name → supplier); components without a match emit NOASSERTION for supplier

### CVE→CWE Enrichment

- [ ] **CWE-01**: For each CVE found via OSV, tool queries NVD API to retrieve associated CWE IDs
- [ ] **CWE-02**: CWE IDs appear as external references in SPDX 2.3 vulnerability output
- [ ] **CWE-03**: CWE IDs populate the CycloneDX 1.5 vulnerabilities.cwes field for xZETA ingestion
- [ ] **CWE-04**: CWE IDs shown alongside CVE entries in the markdown/console vulnerability report

### Internal Feature Gate

- [ ] **GATE-01**: CVE scanning (OSV API) and CWE enrichment (NVD API) are gated behind `cargo feature = "internal"` and compile out of the default build
- [ ] **GATE-02**: `build-release.yml` passes `--features internal` when building the internal release binary
- [ ] **GATE-03**: `public-release.yml` strip script is simplified to verify `internal` is absent from Cargo.toml default features (compiler enforces exclusion; source deletion no longer needed)
- [ ] **GATE-04**: Existing public-release audit step passes cleanly against the feature-gated source tree

## Future Requirements

### AUTOSAR (v1.0.16+)

- **ARXML-01**: Tool parses .arxml files to extract SWC names and interfaces as SBOM components
- **SUP-01**: Tool infers supplier from directory structure (Vector/, EB/ prefixes) without requiring config file
- **CERT-01**: Map AUTOSAR BSW components to ISO 26262 safety integrity levels (ASIL) if declared in .arxml

### Vulnerability (v1.0.16+)

- **SA-01**: Static analysis integration (cppcheck / semgrep) for CWE detection independent of known CVEs

## Out of Scope

| Feature | Reason |
|---------|--------|
| ARXML parsing | High complexity; component identification via heuristics is sufficient for v1.0.15 compliance use case |
| Full Makefile variable expansion | Already deferred in v1.0.14; out of scope |
| Static analysis for CWEs | Deferred to v1.0.16+; NVD enrichment covers the v1.0.15 need |
| .NET / NuGet support | Backlogged |
